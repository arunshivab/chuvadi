# E-0032: Memory during a parse (patch 10, D-303, issue #94)

- Hypothesis: revision 7 keeps far more data alive at a collection than a parse needs. gate mem shows a jump from 512 KiB (2.3 MiB alive) to 1 MiB (108 MiB alive), not a slope, which points to an array of the parse growing past the large-object size (about 85 KB). Such an array is collected only with gen2, and until then the young objects it points to are kept alive and promoted at every gen0 and gen1 collection.
- Cases: gate mem (512 KiB, 1 MiB and 2 MiB documents from the spec text); every gate output for the no-change check.
- Command: gate mem; own probes: promoted bytes at each natural collection over 100 parses; a full collection right after one; live data sampled through a parse; the same with a 32 MiB gen0 and with the large-object threshold raised to 256 KiB (diagnosis only, DOTNET_GCgen0size and DOTNET_GCLOHThreshold).
- Findings:
  - The finished 1 MiB tree is 4.3 MiB, and nothing outlives a parse. Live data during a parse stays under about 8 MiB. Yet a natural gen0 collection with this machine's 240 MiB gen0 budget promoted about 53 MiB, and the heap shrank to 11.9 MiB right after when collected fully: the rest was dead data kept alive by older objects.
  - The holder was the parse-wide list of blocks waiting for inline parsing (block, content pairs, 40 bytes each): at 1 MiB its backing array is on the large object heap and points to every block's content and node.
  - At 2 MiB a second holder remains: the document's child list (14,418 top-level blocks, a 16,384-entry array) in the given MarkdownNode class, which is not mine to change. With the large-object threshold raised for diagnosis, 2 MiB also falls to 0 gen2 and at most 8 MiB promoted.
- Before (revision 7, this machine, 2 cores, gate mem):
  - 512 KiB: 43.5 M chars/s, 27.1 bytes allocated per char, 0 gen2 GC per round, 2.3 MiB alive at a GC
  - 1 MiB: 24.7 M chars/s, 27.1 bytes per char, 0 gen2 GC per round, 108.0 MiB alive
  - 2 MiB: 24.8 M chars/s, 26.8 bytes per char, 0 gen2 GC per round, 107.0 MiB alive
- After (revision 8, R-MD-0279, gate mem):
  - 512 KiB: 52.0 M chars/s, 26.9 bytes allocated per char, 0 gen2 GC per round, 2.0 MiB alive at a GC
  - 1 MiB: 35.4 M chars/s, 26.8 bytes per char, 0 gen2 GC per round, 4.2 MiB alive
  - 2 MiB: 20.0 M chars/s, 26.6 bytes per char, 0 gen2 GC per round, 76.7 MiB alive
- Throughput on this machine varies by up to about 20% between runs, so the two revisions were also run alternately, three times each. At 512 KiB revision 7 gave 46.8, 46.0, 53.4 and revision 8 gave 43.0, 50.2, 49.8 M chars/s; at 1 MiB 25.6 to 25.8 against 34.7 to 35.1; at 2 MiB 20.6, 25.4, 24.7 against 21.5, 26.0, 25.4. The alive figures repeated exactly. No size is worse. This machine never showed a gen2 collection per round, even for revision 7 (the reference machine showed 1 at 1 MiB).
- Output: unchanged (full gate).
- Conclusion: R-MD-0279. The 1 MiB goal is met. The 2 MiB figure is better but still high; the rest is in the given library's child list.
