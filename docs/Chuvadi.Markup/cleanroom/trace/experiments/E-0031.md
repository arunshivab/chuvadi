# E-0031: Cancellation responsiveness (patch 9)

- Hypothesis: The cancellation check added in patch 9 fails because the inline parser and the email pass never poll the token; only the block parser (every 4,096 lines) and the loop between blocks do, so one long paragraph runs to its end.
- Cases: the 12 GateCancel shapes in gate time; also four own shapes (email addresses, entities, escapes, strikethrough runs) and cancels spread over the whole run, not only at 20, 120 and 300 ms.
- Command: gate time --phase P4; own timing program (cancel at 25 points through each run, measuring the delay after the cancel, when the cancel timer fired, and the GC pause time).
- Before / after: before, LATE on brackets ('[' x 3M, cancel not seen, 0.85 to 1.25 s), code spans ('`a' x 3M, seen 1.27 to 1.46 s late) and extended autolinks ('www.a ' x 1M, seen 0.94 to 1.51 s late); the emphasis shape passed on this machine. After R-MD-0273 every shape passes; at the gate's cancel times the worst delay is about 0.3 s.
- Remaining delay: cancels later in long runs (300k list items, a 200k-row table, 100k sections) are sometimes up to about 0.8 s late. In every such run the cancel timer itself fired late by the same amount, during garbage-collection pauses (up to about 0.8 s of pause in a 1.8 s run on 2 cores); once the token was cancelled the parser saw it within a few ms. This delay is in the runtime, not in a loop of the parser; less allocation would shorten it.
- Output: unchanged (the full gate gives the same results).
- Conclusion: R-MD-0273.
