# E-0034: Small documents (patch 13, D-368, D-249)

- Hypothesis: revision 9 allocates a fixed buffer on every parse. An allocation census of 20,000 parses of "a" shows it: almost all sampled allocation is arrays of the inline work list's entry type, the 1,024-entry first chunk (16 KB) that R-MD-0279 (revision 8) allocates up front, whatever the input.
- Cases: the D-368 Small check (1,354 spec examples of the commonmark, gfm-spec and gfm-extensions sets, default options); every gate output; gate time; gate mem.
- Command: gate run --phase P4; gate time --phase P4; gate mem; own probes built against each revision: bytes per parse of five tiny inputs; parse speed of the 1,354 spec examples (best of 7); the gate's documents set, parse + render (best of 5). All figures below are with patches 2 to 13 (patch 12's MarkdownNode), on this machine (2 cores), revisions run alternately.
- Before (revision 9):
  - Small (D-368): NOT PASSED, 702.1 bytes allocated per char; Storage passed
  - bytes per parse: "a" 19,072; "# h\n" 19,080; "- a\n- b\n" 21,536; "`c` *e* [l](u)\n" 21,600; "a|b\n-|-\nc|d\n" 25,064
  - spec examples: 7.6, 7.6 and 7.5 M chars/s
  - documents set: 39.6, 40.8, 39.8 and 40.7 M chars/s (mean 40.2)
  - gate mem, four rounds: 512 KiB mean 46.3 M chars/s, 1.9 MiB alive; 1 MiB 33.9, 4.1 MiB; 2 MiB 33.0, 8.5 MiB; 4 MiB 34.1, 13.3 MiB; 0 gen2 per round at every size; 26.7 to 27.1 bytes allocated per char
- Changes: the first chunk starts at 4 entries and doubles up to 1,024; the emphasis pass no longer allocates its 14-entry table when there is no delimiter run. A search of my code found no other buffer of fixed size.
- After (revision 10, R-MD-0281):
  - Small (D-368): passed, 163.0 bytes allocated per char (at most 175; the BRIEF gives 159.4 for revision 7, 1.1.0's parser); Storage passed
  - bytes per parse: "a" 2,752 (the BRIEF gives 2,688 for 1.1.0); "# h\n" 2,760; "- a\n- b\n" 5,216; "`c` *e* [l](u)\n" 5,280; "a|b\n-|-\nc|d\n" 8,744

  - documents set: 43.2, 40.8, 43.1 and 41.1 M chars/s (mean 42.1)
  - gate mem, four rounds: 512 KiB mean 45.4 M chars/s, 1.9 MiB alive; 1 MiB 34.3, 4.1 MiB; 2 MiB 32.2, 8.5 MiB; 4 MiB 34.1, 13.2 MiB; 0 gen2 per round at every size; allocation per char unchanged
- Run order: in the first two gate mem rounds revision 9 ran first and revision 10 came out 2 to 4% lower at every size; with revision 10 first, the next two rounds came out level or the other way. Over the four rounds the means differ by at most about 2.5%, in both directions. Speeds at large sizes are the same within this machine's noise; nothing large changed.
- An earlier measurement, before patch 12 arrived (patch 11's MarkdownNode), gave the same picture: 702.1 to 163.0 bytes per char, "a" 19,289 to 2,833 bytes.
- Output: unchanged (353,669 outputs; Spans and Storage passed).
- Conclusion: R-MD-0281.
