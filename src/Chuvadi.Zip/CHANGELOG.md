# Chuvadi.Zip - Changelog

## 1.0.2 (2026-11-24)

Security patch (audit findings Z-01, high, and Z-02, medium). Upgrade before opening archives from outside your own system.

**Behaviour change (security).** A `ZipReader` opened with default options now enforces the `ZipExtractionLimits.Untrusted` values. Before, the default was `ZipExtractionLimits.None`, so a zip of about 1 MB holding one 1 GiB entry of zeros wrote 1 GiB to disk (or held 1 GiB in memory) with default options. The same call now throws `ZipLimitExceededException` before any data is produced.

- **New default for `ZipReaderOptions.Limits`:** `ZipExtractionLimits.Untrusted`: at most 10,000 entries, 512 MiB per entry, 2 GiB in total, a compression ratio of 200 (entries under 1 MiB are exempt), 32 levels of folders, 1,024 characters per name and a 64 MiB central directory. Every read path uses it: all `ZipReader.Open` overloads, the extension methods (`ExtractTo`, `ExtractToAsync`, `ListZipEntries`, `ReadZipEntry`), `OpenRead`, `ReadAllBytes`, `ReadAllText`, `CopyTo`, `CopyToAsync`, `Verify` and every `Extract*` method, from a path, from memory and from a non-seekable stream.
- **Who is affected:** code that reads archives with an entry over 512 MiB, more than 2 GiB in total, more than 10,000 entries, or a ratio over 200 on an entry of 1 MiB or more. They now get `ZipLimitExceededException`. For archives you trust, say so: `new ZipReaderOptions { Limits = ZipExtractionLimits.None }`, or set your own `ZipExtractionLimits`.
- **Extraction no longer replaces existing files by default (audit finding Z-02):** `ZipExtractOptions.Overwrite` now defaults to `ZipOverwritePolicy.Fail`, as .NET's own `ZipFile.ExtractToDirectory` does. Extracting an entry whose file already exists throws `IOException` ("File already exists") and leaves that file as it was. Before, the default was `Overwrite`, so a crafted archive could silently replace files in the target folder. Extracting into a new, empty folder is unaffected. To replace files on purpose: `new ZipExtractOptions { Overwrite = ZipOverwritePolicy.Overwrite }`; to keep them and carry on: `ZipOverwritePolicy.Skip`. Note that an archive holding two entries with the same name now fails on the second one instead of "last one wins".
- **`Limits` can no longer be null:** setting it to null throws `ArgumentNullException` (use `ZipExtractionLimits.None` for no caps).
- **Windows file names on extraction:** on Windows, an entry whose name has a segment that is a device name (`CON`, `NUL`, `COM1`, `LPT1` and so on, with or without an extension), ends in a dot or a space, or has a character that is not valid in Windows names (`< > " | ? *` or a control character) is now treated as an unsafe path: `ZipUnsafePathException`, or skipped with `ZipUnsafePathPolicy.Skip`. Other platforms are unchanged. Two entries that differ only in letter case still land on one file on Windows and macOS; `ZipOverwritePolicy` decides which one wins.
- **Known limit (documented, not changed):** the preset allows 2 GiB in total, and entries under 1 MiB are exempt from the ratio check, so a small archive of thousands of such entries can still write up to 2 GiB (measured: a 4.5 MB archive produced 2 GiB, about 475 times its size, before the total cap stopped it). A cumulative ratio limit is planned for 1.1.0. If your app needs a lower ceiling, set your own `MaxTotalBytes`.
- **Tests:** `DefaultLimitsTests` (32 cases): the default values, null refused, the Z-01 archive refused on every read path with nothing left on disk, ratio, entry count, depth and name length, the `None` opt-out, an ordinary archive unaffected, the Windows rules, and the overwrite policies (default `Fail` keeps the existing file; `Overwrite` and `Skip` still work). Three existing tests that built hostile or very large archives, or extracted twice, now set `Limits = None` or `Overwrite` explicitly.
- **Documentation:** `GUIDE.md`, the package README, `SECURITY-MODEL.md` and `PLATFORMS.md` describe the new default and the opt-out.

## 1.0.1 (2026-11-15)

Package metadata, tests and documentation only. No API change and no change in behaviour: the library code is the same as 1.0.0.

- **Trimming and NativeAOT metadata (D-227):** the package now carries `IsTrimmable` and `IsAotCompatible`. The 1.0.0 package did not. The trim analyzers report 0 warnings, and CI publishes a small app that uses Zip with `TrimMode=full` and as NativeAOT (linux-x64), with warnings as errors, and runs it on every change. ReadyToRun is not tested.
- **Tests:** new group `InMemoryPasswordEntryTests` (10 tests, 12 cases) pins the case of opening one entry of an encrypted archive held in memory: AES-128/192/256 from `byte[]`, `ReadOnlyMemory<byte>` and `Stream`; a missing or wrong password throws `ZipPasswordRequiredException` (`WrongPassword` false for a missing one) for both AES and ZipCrypto; `MaxEntryBytes`, `MaxCompressionRatio` and the `Untrusted` preset stop an entry with `ZipLimitExceededException` while a small entry in the same archive still reads; bytes that are not a zip throw `ZipFormatException`.
- **Documentation:** `GUIDE.md` has a section "One entry from memory, with a password and limits"; `PLATFORMS.md` is brought up to date (the 1.0.0 package lacks the trim metadata; macOS and Android now run in CI, not yet as required checks).

## 1.0.0 (2026-11-06)

First release. A complete zip engine written for this library (it does not wrap `ZipArchive`), built only from the BCL (`DeflateStream`, `Aes`, `Rfc2898DeriveBytes`, `HMAC`).

- **Reading**: `ZipReader.Open(path | byte[] | Stream)`, `OpenAsync`; non-seekable input is buffered in memory only (cap `MaxBufferedBytes`), never on disk. Entry list, `FindEntry`, `OpenRead`, `ReadAllBytes`, `ReadAllText`, `CopyTo(Async)`, `Verify`, `ExtractTo(Async)`, `ExtractEntries(Async)`. Archive prefixes (self-extractor stubs) handled.
- **Writing**: `ZipWriter.Create(path | Stream)`, `ToBytes`; `CreateEntry` (stream), `AddBytes`, `AddText`, `AddStream(Async)`, `AddFile(Async)`, `AddDirectory`, `AddDirectoryTree(Async)`. Seekable outputs patch headers; non-seekable outputs use data descriptors.
- **Zip64**: read everywhere; write in `Auto`, `Always` or `Never` mode. A streamed entry that may exceed 4 GiB must declare `ExpectedSize` or `Zip64`, otherwise the writer throws `ZipLimitExceededException` (it never silently writes a corrupt archive).
- **Encryption**: WinZip AES-128/192/256, AE-1 and AE-2, read and write, HMAC verified (read side drains to the authentication code). ZipCrypto read only; writing it throws `ZipUnsupportedException`.
- **Safety**: `ZipExtractionLimits` (+ `Untrusted` preset), zip-slip rejection (`..`, rooted, drive letters, `:`, NUL, backslashes), `ZipUnsafePathPolicy`, `ZipSymlinkPolicy`, `ZipOverwritePolicy`, refusal to write through links, overlapping-entry detection, declared-size enforcement against actual output, partial-file cleanup on failure.
- **Metadata**: comments, DOS time + `0x5455` extended timestamp, Unix mode, DOS attributes, raw external attributes, host system; UTF-8 flag, CP437 fallback (configurable), Info-ZIP Unicode path (`0x7075`).
- **Exceptions**: `ZipFormatException` base with `ZipLimitExceededException`, `ZipUnsafePathException`, `ZipIntegrityException`, `ZipUnsupportedException`; `ZipPasswordRequiredException` (missing or wrong password; also thrown, with the `ZipIntegrityException` as `InnerException`, when a ZipCrypto entry passes the format's one-byte password check and then fails its CRC-32 or decompression check, because a wrong password gets through that check about 1 time in 256 and cannot be told apart from damage. AES and unencrypted entries are unaffected).
- **Not in 1.0**: BZip2/LZMA/Deflate64/PPMd/strong-encryption entries (reported as unsupported, listable), split archives, forward-only (no-seek) reading, RAR and 7z.
- `Chuvadi.Sheets.Zip` is unchanged; it will be marked obsolete in favour of this package in a later Sheets release.
